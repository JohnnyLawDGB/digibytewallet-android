# Handoff — Wallet Sync, Asset Accounting & Restore Flow

**Repo:** `JohnnyLawDGB/digibytewallet-android`
**Date:** 2026-08-16
**Status:** Design decisions made. Implementation not started. All three specs below are
*investigation-first* — they assert the target architecture, not the current one.

---

## 1. Primer — what we are actually trying to accomplish

The wallet's privacy model rests on BIP157/158 compact block filters: the client
downloads filters, tests them locally against its own script set, and only requests
full blocks on a match. The server never learns which addresses belong to the user.

Three things currently undercut that model or sit on top of it incorrectly:

**(a) A privacy hole in restore.** The "restore old keys" path derives the address set
and then queries an ElectrumX endpoint directly for balances and UTXOs. That hands the
server operator a complete map of the wallet in one request — which nullifies the entire
reason we implemented BIP158. Today that endpoint is DigiScope infrastructure (operated
by me), so the leak is contained, but shipping it means every user's address set is
exposed to whoever runs the node.

**(b) Asset balances are wrong.** DigiAsset quantities are accumulated by replaying
transaction history during sync. Replay-based accounting drifts and never self-corrects.
Concrete failure: issue an asset with supply 10, send 1. Chain and explorer both agree
the wallet holds 9. Wallet reports 18.

**(c) Peer handling is wasteful.** The filter sync layer churns through ~8 peers with
proactive pinging rather than holding a small number of proven-good connections.

The unifying principle across all three: **derive state from what the chain currently
says, hold connections we've already proven good, and never let a convenience path leak
the address set the filter layer was built to protect.**

Sequencing matters because (b) blocks the `assets.digistamp.co` marketplace integration —
there is no point wiring a marketplace on top of balances we can't trust — and (a) is
the gating item for removing the DigiScope ElectrumX dependency from the shipped app.

## 2. What changed in the plan

| Item | Decision |
|---|---|
| Duress code workflow | **Removed.** Not proceeding. Strip from roadmap, specs, and any scaffolding already in the tree. |
| Restore in onboarding | **Removed from primary path.** New users always generate a fresh wallet. Restore becomes a separate side flow. |
| DigiScope ElectrumX endpoint | **To be stripped from the app.** Replaced by user-supplied node instructions + filter-based rescan. |
| Asset balance source | **UTXO set**, not transaction-history replay. |
| Filter peer strategy | **Sticky 2 + warm standby**, not churn-through-8. |
| `assets.digistamp.co` integration | **Backlog.** Gated on the asset accounting fix landing. |

## 4. Prioritization and insertion into the current workflow

Suggested ordering, with reasoning rather than just numbers:

**P0 — Spec 1 (asset accounting).**
Do this first. It is the smallest well-defined unit, it has a concrete reproducible
failure case, it is largely independent of the network layer, and it unblocks the
marketplace integration. It also de-risks Spec 3: asset-aware sweeping is only safe if
we can trust the parser's per-UTXO quantity resolution, which is exactly what Spec 1
establishes.

**P1 — Spec 3 (restore flow).**
Second, because it is the item with a live privacy consequence and it depends on Spec 1's
per-UTXO asset resolution. Split it: the onboarding restructure (fresh-wallet-by-default,
restore moved to a side flow) can land ahead of the asset-aware sweep, and should, since
it immediately removes the ElectrumX call from the default user journey.

**P2 — Spec 2 (peer retention).**
Third. It is independently landable at any time and touches no asset code, so it can be
picked up in parallel or slotted in whenever P0/P1 are blocked on review. It improves
sync reliability and battery behavior but nothing depends on it.

**Removal task — duress code.** Do this immediately, ahead of everything, if any
scaffolding exists in the tree. It's a delete, not a design task, and leaving dead
security-adjacent code in the repo is worse than not having written it.

**Backlog — `assets.digistamp.co`.** Do not start until Spec 1 is merged and validated
against the DigiAsset Core explorer.

## 5. Instructions for the coding session

Paste something close to this as the opening message:

> Read `docs/specs/digiasset-balance-accounting.md`. Before writing any code, do the
> investigation section first and report back: how does the wallet currently compute
> DigiAsset balances, where does the parser get per-UTXO asset quantity, and can you
> reproduce the 10-issue / send-1 / reports-18 case in a test? Do not begin the
> refactor until we've confirmed the root cause matches the hypothesis in the spec.

Two standing instructions worth repeating to the session:

1. **Investigate before refactoring.** Every spec here contains assumptions about code
   I have not re-read. If the code disagrees with the spec, the code wins — report the
   discrepancy rather than bending the implementation to match a wrong assumption.
2. **Validate against ground truth, not against the wallet.** The DigiAsset Core node and
   the DigiScope explorer are authoritative. A passing unit test that agrees with the
   wallet's own accounting proves nothing; a balance that agrees with the explorer's view
   of the asset ID does.
