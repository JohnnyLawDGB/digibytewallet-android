# CF Scan-Ledger Stale-Buffer Livelock + Exclusive-Pin Enforcement — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Fix the mainline production livelock where stale buffered cfilters (orphaned by a header re-sync) starve the buffer-gated residual re-request for every height, and enforce `custom_node_exclusive` against public priority-peer injection. Both surfaced by the Phase-2 acceptance rig (2026-07-26): the $1 DD at block 23,920,918 did NOT credit via CF; `outstanding` pinned at 2000, `scannedThrough` frozen, `gaveUp` 0.

**Architecture:** Two independent tracks. **Track A** (SHIPPED — PR #35 merged): pin-enforcement guard + a per-block diagnostic-log demotion. **Track B** (this plan, drain-core, hostile-reviewed & revised): fix the stale-buffer / residual-gating livelock by **deleting the global buffer gate**, adding a cheap O(bufCount) **reverse-mapping suppressor** so residual re-requests only genuine holes, and an **age-out** byte-reclamation backstop.

**Tech Stack:** C (breadwallet-derived native core, submodule `digibytewallet-core`), JNI bridge (outer repo `native/src/main/jni/bridge/`), host KATs (`scripts/run-host-kats.sh`, ASan).

## Reframe that motivates this (do not re-litigate)
Multi-peer public-fleet discovery **is the product**; own-node-exclusive is an optional mode + test instrument. So cfilters-from-one-peer-while-headers-climb-from-another, peer-drop header re-syncs, and racing chain views are **normal production behavior**, not a polluted test. The stale-buffer livelock they produce is a **mainline day-one blocker**, not a follow-up. Buffered bytes are an *optimization*; the ledger's `outstanding` record is the source of truth — so **evicting a buffered entry is always safe** (worst case, the height stays outstanding and residual re-requests it).

## Hostile-review outcome (2026-07-26 — folded in here; do not re-derive)
The first Track B design (three tasks: evict-on-mismatch, per-height eligibility via a forward `canonical(H)` walk, age-out) went to a hostile design review. Verdict **DESIGN-NEEDS-REVISION**, and the revision is strictly **smaller and safer**:

- **CRITICAL (fixed here):** the original Task 4 resolved `canonical(H)` by a `prevBlock` main-chain walk from the tip down to H. In the exact floor/recovery regime where the livelock lives, tip races **thousands of blocks** ahead of the cfheader frontier, so that walk is thousands of derefs **per candidate, ×64/tick, under `manager->lock`** — the PEER_GUARD hold-time ANR class this codebase keeps hitting, and the class #33's lock-free reads exist to escape. A host KAT (few blocks) makes the walk cheap → it would ship **green with the pathology** (false-green-for-perf). **Fixed by reversing the lookup:** never compute `canonical(H)` forward. Enumerate the small buffered set (≤ `filterBufCount`), resolve each `blockHash → BRSetGet(manager->blocks)` O(1), build a tiny "buffer-owned heights" skip set. No walk anywhere.
- **The load-bearing fix is deleting the global `if (BufferedCount()==0)` gate** (`BRPeerManager.c:3245`) — that one line is what breaks the livelock and what fixes the observed `gaveUp==0` (RetireCapped, at `:3246`, lives inside the gate → never runs while the buffer is non-empty). Per-height eligibility is then a **volume** refinement (the reverse-mapping suppressor), not a correctness requirement.
- **Task 5 (evict-on-mismatch) DROPPED** (deviation ledger below) — redundant with the existing verify-fail at `_cfBufEval:3172` (which already evicts a stale entry in O(1) **without** MarkEvaluated), and it would reintroduce the walk to detect what verify-fail detects for free.
- **Age-out is byte-reclamation, NOT a livelock cure.** "Age-out guarantees BufferedCount→0" is FALSE under churn + the `e->at = now` re-buffer reset. Kept as a byte-budget backstop only, re-keyed off an **immutable first-buffered timestamp**, guarantee-framing removed.

## Request-volume analysis of the gate deletion (the crux the review demanded proven, not asserted)
**Claim:** deleting the `BufferedCount()==0` gate is safe *and* does not create a per-tick re-request storm; the reverse-mapping suppressor trims a bounded remainder.

**Grounded from `BRPeerManager.c:3245-3286` + `BRCFScanLedger.h:78-93`:**
1. **The residual path was already self-throttled — the "storm" premise is false.** `BRCFScanLedgerPeekRerequestRange` offers only holes whose backoff has **elapsed** (pinned schedule: header-race 10s first, else `CF_REREQ_BASE_SECS 30` → 30/60/120/120/120). Each height is hard-capped at `CF_REREQ_MAX_ATTEMPTS`=5, then `RetireCapped` moves it to `gaveUp` and it is never offered again. Per tick the loop runs at most `CF_REREQ_BATCH_PER_TICK`=64 coalesced ranges (≤ `CF_REREQ_MAX_RANGE`=1000 heights each). So the **absolute worst-case re-request volume for any height is 5 cfilter fetches over ~7.5 min** — bounded, whether the gate is present or not. Deleting the gate cannot produce an every-tick doubling; it re-enables an already-rate-limited path.
2. **Correctness of a duplicate re-request:** harmless. `BufferFilter` de-dups by blockHash (a re-buffer replaces bytes in place); the drain credits correctly; `BRWalletRegisterTransaction` de-dups on the wallet side; `MarkEvaluated` is idempotent.
3. **What gate-deletion *does* add without a suppressor:** redundant cfilter re-fetches for heights that are simultaneously outstanding **and** hold buffered-but-undrained bytes. Two sub-populations:
   - **cfheader-lag** (header connected, cfheader not yet — `_cfBufIsReady:3162` returns 0): the buffered `blockHash` **is** in `manager->blocks`, so the reverse map resolves it → height → **skip**. Zero redundant fetch. This is the **dominant** buffered population in a floor cluster (headers sync first/fast; cfilters race ahead of cfheaders).
   - **header-race** (header not connected — `_cfBufIsReady:3161` returns 0 on `BRSetGet==NULL`): height ↔ buffered blockHash are **unlinkable** until the header connects, so the suppressor cannot skip these. They may be re-fetched **only if the header lags past the 10s header-race retry**; in the common case the drain evaluates + `MarkEvaluated` removes them within a tick or two (well under 10s) → zero redundant fetch. A genuinely slow-header cluster costs bounded (backoff × 5-cap) duplicate cfilter traffic.
4. **Suppressor status — RESOLVED: KEEP it** (not "optional"). It is a cheap O(`filterBufCount`) reverse map built **once per tick** (≤ `CF_FILTER_BUF_SLOTS`=2048 O(1) `BRSetGet`s) that eliminates redundant re-fetch of the **dominant** (cfheader-lag) buffered population — real savings in the exact fresh-sync regime where mobile bandwidth matters most. It is a **volume** refinement layered on the already-bounded backoff, not the thing preventing a storm (the backoff is). Net residual wire volume with the suppressor ≈ the intended pre-livelock design.

## TRACK B — stale-buffer / residual-gating livelock (drain-core, hostile-reviewed & revised)

**The livelock (root cause, from the rig):** buffered cfilters are keyed by blockHash; a header re-sync (normal multi-peer behavior) replaces the chain view, orphaning those hashes; orphaned entries never become "ready" to drain; and the residual re-request is gated on the GLOBAL `BufferedCount()==0` (`BRPeerManager.c:3245`), so a handful of undrainable stale entries starves re-request for EVERY height. `outstanding` pins, `gaveUp` stays 0 (RetireCapped, `:3246`, sits inside the gate) — a livelock with perfect visibility and no exit.

**Fix shape (revised):** delete the gate (correctness); add the reverse-mapping suppressor (volume); age-out reclaims bytes (backstop). No forward walk, no evict-on-mismatch task, no new silent-loss surface.

### Task 4: delete the global buffer gate + O(1) reverse-mapping residual suppressor (the load-bearing fix)

**Files:** Modify `native/src/main/jni/digibytewallet-core/BRCFScanLedger.c`/`.h` (add the pure enumerator); Modify `native/src/main/jni/digibytewallet-core/BRPeerManager.c` (`:3245-3286` residual block, drain the age-out each tick); Test `native/src/test/host/cf_scan_ledger_kat/` (enumerator) + `native/src/test/host/cf_scan_ledger_drive_kat/` (residual wiring).

**Design (no forward walk anywhere):**
1. **Delete** the `if (BRCFScanLedgerBufferedCount(&manager->cfLedger) == 0) {` wrapper (`:3245`) and its matching close brace. `RetireCapped` + the peek/commit loop now run every tick regardless of buffer state. This alone breaks the livelock. **Intended consequence — `RetireCapped` becomes live (read this before touching the acceptance metrics):** pre-fix, `RetireCapped` sat *inside* the shut gate, so a stale buffer froze it → `gaveUp` was structurally stuck at 0, a vacuous tripwire that could never fire even under genuine dead-hole failure. Post-fix it runs every tick, so a height that truly exhausts `CF_REREQ_MAX_ATTEMPTS`=5 (dead peers, a permanent header stall, a block no connected CF peer will serve) now correctly retires to `gaveUp` — the "reported, never silently dropped" contract (`BRCFScanLedger.h:149-150`) finally operating as designed. This is the desired behavior, not a side effect to be nervous about. See the gaveUp-semantics note in Acceptance: `gaveUp` is now a diagnostic signal, and `outstanding` (not `gaveUp`) remains the primary wedge alarm.
2. **Call `BRCFScanLedgerEvictAgedFilters(&manager->cfLedger, nowSec)`** once per tick (right after `DrainConnected` at `:3243`), so the byte backstop runs.
3. **Add a pure enumerator** `size_t BRCFScanLedgerBufferedHashes(const BRCFScanLedger *l, UInt256 *out, size_t cap)` — copies up to `cap` buffered blockHashes into `out`, returns the count. O(`filterBufCount`), holds no locks, no `manager` dependency (keeps the ledger module pure).
4. **Build the skip set once per tick in BRPeerManager** (which owns `manager->blocks`): enumerate buffered hashes; for each, `BRMerkleBlock *b = BRSetGet(manager->blocks, &hash)`; if `b && b->height != BLOCK_UNKNOWN_HEIGHT`, add `b->height` to a small stack skip array (bounded by `CF_FILTER_BUF_SLOTS`). Orphaned/pruned/header-not-connected hashes resolve to NULL → contribute no height → suppress nothing (correct: their outstanding heights get re-requested). This is the reverse map — **never** compute canonical(H) forward.
5. **Apply the skip in the peek loop:** when `PeekRerequestRange` offers `[rs..re]`, if `rs` is in the skip set, advance `minH = rs + 1` and `continue` — reusing the existing skip-past idiom already at `:3252` (`if (cap < rs) { minH = re + 1; continue; }`). A buffered height sparse in the middle of a coalesced run may still ride along in a range — that is the harmless, bounded (backoff × 5-cap) redundant fetch quantified in the volume analysis, acceptable and self-limiting.

## gaveUp semantics post-fix (interpretation for anyone reading the metrics — was a should-always-be-0 tripwire, is now a live diagnostic)
Because Task 4 makes `RetireCapped` run, `gaveUp` changes meaning and the acceptance/field wording must match:
- **Healthy run** (both acceptance runs below, and a normal field session): `gaveUp` should be **0**. Every requested height is evaluated because the fleet serves the filters and the residual driver drains any transient holes. A nonzero `gaveUp` *in the controlled acceptance runs* is worth investigating — the fix is supposed to let everything drain there.
- **Field, nonzero `gaveUp`:** **diagnostic information, NOT automatically a bug.** It means exactly "these specific heights exhausted 5 honest retries over ~7.5 min and are parked — reported, never silently dropped." That is `gaveUp` doing its job (surfacing a real fetch failure — e.g. a block no currently-connected peer will serve), not a wedge. Do not alarm on `gaveUp > 0` alone.
- **The primary wedge alarm is still `outstanding` not draining**, per the alarm-promotion decision: a genuinely large dead cluster can exceed `CF_GAVEUP_MAX`=512, so the remainder stays `outstanding` — which is precisely why `outstanding` (rising/pinned, not falling toward 0) is the wedge signal, and `gaveUp` is the "we tried honestly and couldn't fetch these" ledger beside it.
