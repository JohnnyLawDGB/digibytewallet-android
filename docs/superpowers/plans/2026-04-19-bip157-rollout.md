# BIP 157/158 Rollout Plan — DigiByte Android Wallet

**Status:** Draft plan, executable by a single engineer or contractor.
**Target version:** v4.0.0 (Phase 1 of ROADMAP.md, "Sovereign data layer").
**Current baseline:** v3.5.16 — SPV with BIP 37 bloom filters.
**Author context:** DigiByte Core 8.26 ships with the full Bitcoin Core v26.2 BIP 157 serving stack (`NODE_COMPACT_FILTERS` = 0x40, `getcfilters`/`cfilter`/`getcfheaders`/`cfheaders`/`getcfcheckpt`/`cfcheckpt`). No upstream Core PR is required; the only server-side work is enabling `blockfilterindex=basic` and `peerblockfilters=1` on at least two independent nodes.

Everything that follows is additive to the existing SPV+bloom path. Bloom is **not** removed in v4.0.0 — it stays as a fallback until service-bit coverage is high enough to retire it in a later minor (see §7, §9).

---

## 0. Current state of the tree (already in repo as of 2026-04-14)

- `native/src/main/jni/digibytewallet-core/BRGCSFilter.{c,h}` — exists, 433 + 103 LOC, compiles cleanly against the Android NDK as of Apr 14 2026. Provides `BRGCSFilterParse`, `BRGCSFilterBasicParse`, `BRGCSFilterMatch`, `BRGCSFilterHash`, `BRGCSFilterHeader`, plus `BR_GCS_MAX_ENCODED_SIZE`.
- `native/src/main/jni/digibytewallet-core/BRGCSFilterTests.c` — 331 LOC, includes BIP 158 appendix vectors and malformed-input tests.
- `BRPeer.{c,h}` — has `SERVICES_NODE_NETWORK` (0x01) and `SERVICES_NODE_BLOOM` (0x04) defined; **no `SERVICES_NODE_COMPACT_FILTERS` (0x40) yet**. `ENABLED_SERVICES = 0ULL` on the client side is correct and does not need to change.
- `BRPeerManager.c` — peer prioritization (lines ~995, 1853–1882) already biases toward NODE_BLOOM; needs extension, not rewrite.
- Kotlin `SyncService.kt` — fetches peers from `https://api.digiscope.me/api/peers/bloom` hourly, injects via `NativeBridge.injectPeerByIp`.
- `NativeBridge.kt` — thin `external fun` surface; no filter-related methods yet.

**What is missing:** P2P message handlers for BIP 157, a filter header chain persistence layer, a filter-sync state machine, the 0x40 service flag plumbing, a filter-capable seeder endpoint, and the Kotlin UI/settings to choose mode. The GCS decoder is already done.

## 1. Native C layer (submodule `digibytewallet-core`)

All work lands in the submodule. Each item below should be a separate commit on a `bip157` branch of `JohnnyLawDGB/digibytewallet-core`, to keep `git log` diffable against upstream breadwallet-core.

### 1.1 Service-bit constants (trivial, land first)

`BRPeer.h` — add:
```c
#define SERVICES_NODE_COMPACT_FILTERS 0x40ULL  // BIP 157
```
Reference: Bitcoin Core `src/protocol.h` `NODE_COMPACT_FILTERS`. Do **not** add this to `ENABLED_SERVICES` — the wallet does not serve filters, only consumes them.

### 1.2 P2P message handlers

Extend `BRPeer.c` message-dispatch switch (~line 1520 region where existing handlers live) with six new handlers, mirroring the structure of existing bloom handlers:

- `_BRPeerAcceptCFilter` — parses `cfilter` response: `filter_type` (u8), `block_hash` (32B), `num_filter_bytes` (compactsize), `filter` bytes. Validates `filter_type == 0` (basic). Invokes `BRGCSFilterBasicParse`.
- `_BRPeerAcceptCFHeaders` — parses `cfheaders`: `filter_type`, `stop_block_hash`, `previous_filter_header`, `num_filter_hashes`, `filter_hashes[]`. Reconstructs each filter header by iteratively calling `BRGCSFilterHeader(prev, hash)`.
- `_BRPeerAcceptCFCheckpt` — parses `cfcheckpt` for quorum verification against shipped checkpoints.

Send-side helpers (construct the request messages):
- `BRPeerSendGetCFilters(peer, filter_type, start_height, stop_hash)`
- `BRPeerSendGetCFHeaders(peer, filter_type, start_height, stop_hash)`
- `BRPeerSendGetCFCheckpt(peer, filter_type, stop_hash)`

**Reference:** Bitcoin Core `src/net_processing.cpp` lines ~3399–3507 in v26.2. The wire format is straightforward; there are no version-gated quirks.

Commit scope: ~300–400 LOC net add, zero changes to existing bloom paths.

### 1.3 Filter header chain persistence (`BRFilterHeaders.{c,h}`)

New files. Responsibilities:
- In-memory chain of `(block_hash, filter_hash, filter_header)` tuples, parallel to the block header chain.
- Serialization to a binary file alongside the existing block-header persistence (current persistence layer: see `BRPeerManager.c` save callbacks).
- API: `BRFilterHeadersAppend`, `BRFilterHeadersGetAt`, `BRFilterHeadersTipHeight`, `BRFilterHeadersVerifyChain(anchor_header, hashes[])`, `BRFilterHeadersRewindTo(height)` for reorg handling.
- Memory footprint: 32 bytes × chain length. At DGB's ~1-minute block time and 16M+ blocks expected by 2030, this is ~500 MB — **not** acceptable. Store only the tip-ward N (e.g. last 100k blocks = 3.2 MB) plus checkpointed anchors every 10,000 blocks.

### 1.4 Hardcoded filter-header checkpoints (`BRFilterCheckpoints.{c,h}`)

Separate from `BRChainParams.h:72–130` block checkpoints. Cadence: **every 10,000 blocks** (ROADMAP §Phase 1 explicitly specifies this). APK impact: ~83 KB for the full chain. Each entry is `{ height: u32, block_hash: UInt256, filter_header: UInt256 }` — 68 bytes.

**Generation:** script (bash/Python, kept in `scripts/gen-filter-checkpoints.py`) that calls `getblockfilter` RPC on the digiscope.me DGB node for every 10,000th block and writes the C array literal. Run once per release to extend toward chain tip.

**Trust model:** shipped checkpoints are bootstrap hints only. Runtime *always* cross-verifies against peer-quorum `cfcheckpt` response. On mismatch: fail sync loudly, surface to UI — never silently trust the shipped array.

### 1.5 Sync state machine (extend `BRPeerManager.c`)

Add a `BRPeerFilterMode` enum: `PEER_FILTER_MODE_BLOOM`, `PEER_FILTER_MODE_COMPACT`, `PEER_FILTER_MODE_NEGOTIATING`. Decision logic:

1. On peer handshake completion, tally connected peers by service bits.
2. If ≥ `PEER_MAX_CONNECTIONS/2` (typically 3 of 6) peers advertise `SERVICES_NODE_COMPACT_FILTERS`, enter `PEER_FILTER_MODE_COMPACT`:
   - Do **not** send `filterload` to any peer.
   - Request `getcfheaders` in batches of 1000 to bring filter header chain to tip.
   - Cross-verify against `cfcheckpt` quorum (≥ 2 peers agreeing on same checkpoints).
   - For each block whose filter matches any wallet script, request the full block with `getdata MSG_BLOCK`.
3. Otherwise enter `PEER_FILTER_MODE_BLOOM` (current behavior).
4. **Mid-stream mode switching.** If compact-filter peers drop below threshold mid-sync, do not tear down completed filter-header progress — persist and resume when coverage returns. Only downgrade to bloom mode after a configurable grace window (suggest 5 minutes) to avoid thrashing.

### 1.6 Peer selection by service bits

Extend the bloom-prioritization code in `BRPeerManager.c:1853–1882` region. New ordering: `NODE_COMPACT_FILTERS` > `NODE_BLOOM` > anything else. The existing "reject non-BLOOM peers" filter at `BRPeerManager.c:995` must be made mode-aware (a peer with 0x40 but not 0x04 is still useful in compact mode).

### 1.7 Test harness wiring

`BRGCSFilterTests.c` is already written but not wired to a runnable target. Add a native Gradle task (or a JUnit shim calling through JNI) that runs `BRGCSFilterTests()` and fails the build on non-zero exit. Run in CI on every PR.

## 2. JNI bridge additions

New methods in `core/src/main/java/io/digibyte/core/bridge/NativeBridge.kt`:

```kotlin
// === BIP 157/158 status ===
/** Current sync mode: 0=uninitialized, 1=bloom, 2=compact_filters, 3=negotiating. */
external fun getFilterSyncMode(): Int

/** Filter header chain tip height (compact-filter mode only; -1 otherwise). */
external fun getFilterHeaderTipHeight(): Long

/** Count of peers advertising NODE_COMPACT_FILTERS in the current connected set. */
external fun getCompactFilterPeerCount(): Int

/** Count of peers advertising NODE_BLOOM. */
external fun getBloomPeerCount(): Int

/** Force bloom-only mode (kill switch). Persists across restart. */
external fun setForceBloomMode(forced: Boolean)

/** Opposite: force compact-filter-only (dev/power-user mode; errors if no filter peers). */
external fun setRequireCompactFilters(required: Boolean)
```

Add corresponding callbacks to `NativeCallback.kt`:
- `onFilterSyncModeChanged(newMode: Int)`
- `onFilterHeaderProgress(height: Long, tip: Long)`
- `onFilterCheckpointMismatch(height: Long, peerCount: Int)` — surface loudly in UI.

Corresponding JNI implementations live in `native/src/main/cpp/` (existing `*_jni.cpp` file pattern).

## 3. Kotlin/Android layer changes

### 3.1 `SyncService.kt`

- Startup dispatch: on service start, if `getFilterSyncMode()` transitions to COMPACT, skip `injectBloomPeers()` and call a new `injectCompactFilterPeers()` instead.
- Keep `injectBloomPeers()` intact — it is the fallback path.
- Surface mode via a `StateFlow<FilterSyncMode>` that UI observes.

### 3.2 Settings screen

New toggle group under a **"Network & Privacy"** settings section:
- **Data source:** radio — `Auto (recommended)` / `Compact filters only (stricter privacy)` / `Bloom filters only (legacy)`. Default `Auto`.
- **Custom full node:** optional text field for `host:port` of a user-run DGB node. If set, the wallet prefers this peer and will send `getcfilters` to it directly. This is the **sovereignty-first escape hatch** the ROADMAP demands — users are never forced to rely on digiscope.me's filter infrastructure.
- **Show current mode:** read-only indicator ("Syncing via compact filters — 4 peers" / "Bloom fallback — 3 peers — your privacy is lower").

Files:
- `app/src/main/java/io/digibyte/ui/settings/NetworkSettingsScreen.kt` (new)
- `core/src/main/java/io/digibyte/core/model/NetworkPrefs.kt` (new, DataStore-backed)

### 3.3 Wallet screen sync banner

Extend existing sync progress UI on `WalletScreen` to show mode. Bloom-fallback banner copy (non-scary): *"Bootstrap via bloom filters — compact-filter peers are currently scarce. Your privacy is lower until coverage grows."* Include a "Learn more" link to `docs/THREAT_MODEL.md`.

### 3.4 Filter header persistence

Native C owns the binary file. Kotlin's only responsibility is exposing its storage path (`context.filesDir / "digibyte/filter_headers.dat"`) to the C core via a path setter, identical to how block headers are handed off today.

## 4. Peer discovery for filter-serving nodes

This is the hardest non-code problem. `NODE_COMPACT_FILTERS` peers are rare in 2026 — the DGB network likely has << 50 globally at rollout. Strategy, in priority order:

1. **Extend the digiscope.me seeder.** New endpoint `https://api.digiscope.me/api/peers/compact` that returns the same JSON schema as `/api/peers/bloom`, filtered by 0x40 advertisement. Also extend the existing `/api/peers/bloom` response to include a `services` integer field per peer, so one endpoint can serve both modes. Server-side work: the existing `dgb-bloom-seeder` crawler already inspects version messages; it just needs to expose the full services bitmask.
2. **Second independent seeder.** Coordinate with one community operator (candidates: existing bloom seeder operators on the DGB Discord) to run a parallel seeder. Goal: the wallet never *requires* digiscope.me for compact-filter discovery. Phase 1 ships with at least two seeder URLs in the codebase.
3. **DNS seed filtering.** The existing DNS seeds return peers regardless of service bits. After connection, probe `version` → discard peers that don't advertise 0x40. Expensive (extra TCP handshakes) but sovereignty-preserving.
4. **User-provided node.** Via settings (§3.2). For power users, this is the right answer — their own `digibyted` with `peerblockfilters=1` is the trust-minimized path.
5. **Hardcoded seed list.** In `BRChainParams.h`, add a curated `compactFilterSeeds[]` array of known 0x40-advertising nodes. Refresh each release. Low-trust baseline for cold start when all seeders are unreachable (offline install, GFW, etc.).

**On-node enablement** (server-side, coordinated with Phase 1 delivery):
- digiscope.me DGB 8.26 node: set `blockfilterindex=basic`, `peerblockfilters=1`, restart. Expect 6–12 GB disk add and 4–12 hours to build the index. Not compatible with `prune`.
- At least one non-author-operated community node doing the same.

## 5. Rollout strategy

### 5.1 Feature flag architecture

Two flags:
- **Build-time:** `enableCompactFilters` in `gradle.properties`, default `true` starting with v4.0.0-beta.1. Allows quick revert to v3.5.x behavior without a code change.
- **Runtime:** the `NetworkPrefs.dataSource` setting (§3.2). User-controllable kill switch.

Native C respects both. If build-time flag is off, the entire BIP 157 code path is `#ifdef`'d out — no risk of accidental activation.

### 5.2 Stage gates (each gate is a go/no-go for the next stage)

1. **Gate A — Native correctness.** `BRGCSFilterTests()` passes in CI. Additional integration test: run wallet against regtest DGB node with `peerblockfilters=1`, verify every filter fetched from the node decodes and its header matches `getblockfilter` RPC output. No wallet UI yet.
2. **Gate B — Testnet behavior.** v4.0.0-alpha flavored against testnet, syncing via compact filters only. Run for one week. Compare final UTXO set against a parallel bloom-filter sync of the same mnemonic — must match exactly.
3. **Gate C — Mainnet dogfood.** v4.0.0-beta.1 to internal testers + opt-in community beta channel. 2-week window. Telemetry (anonymous, opt-in, no address data): sync mode chosen, peer counts, checkpoint mismatches, fallback-to-bloom events, sync duration deltas.
4. **Gate D — Staged public release.** v4.0.0 to F-Droid/GitHub first (smaller user base, faster rollback). 1 week bake. Then Play Store if applicable.
5. **Gate E — Bloom retirement (future, likely v4.2+).** Only after telemetry shows >80% of installs successfully complete sync in compact mode without bloom fallback. Flip the build-time flag to disable bloom, ship as v5.0.0 major.

### 5.3 Rollback plan

If Gate C surfaces a chain-safety bug (e.g. checkpoint mismatch under benign conditions): ship a patch that flips the runtime default to `Bloom filters only`. No data migration needed — the filter-header chain persistence is additive; dropping it does not corrupt anything. Affected users' next sync silently returns to bloom.

## 6. Testing strategy

### 6.1 Unit tests (native)

- BIP 158 appendix vectors (already in `BRGCSFilterTests.c`). Wire to CI (§1.7).
- Filter header chain construction from a recorded `cfheaders` capture.
- Checkpoint verification: ship a deliberately wrong hardcoded checkpoint, confirm the runtime cross-verification catches and loudly fails.

### 6.2 Integration tests

- **Regtest node parity.** Local regtest DGB 8.26 with filter index. For 1000 generated blocks, confirm: `BRGCSFilterBasicParse` output matches `getblockfilter` RPC; `BRGCSFilterHeader` iteration matches the RPC-reported filter header; `BRGCSFilterMatch` returns true iff the address appears in the block.
- **Golden-path mainnet sync.** Fresh wallet seeded with known-to-receive mnemonic, synced via compact filters only against digiscope.me node. Assert final UTXO set matches Insight/Blockbook for the same addresses.
- **Reorg.** Induce a 6-block reorg on regtest. Verify filter header chain rewinds and resyncs correctly.
- **Peer churn.** Start in compact mode, kill all filter-serving peers mid-sync, assert clean fallback to bloom without duplicate transactions or balance drift.

### 6.3 Negative tests

- Hostile peer sends malformed `cfilter` → peer disconnected, no crash.
- Peer sends `cfheaders` with inconsistent `previous_filter_header` → chain not extended, peer penalized.
- `cfcheckpt` quorum split (2 peers disagree) → sync halts, UI surfaces warning.

### 6.4 Manual QA checklist

Maestro flows (`maestro/` already in repo): new `bip157-sync.yaml` covering fresh install → observe compact-filter mode → settings toggle → force-bloom-mode → verify fallback UI.

## 7. Fallback behavior when no filter peers are available

Priority: **do not dead-end users.** The ROADMAP is explicit — bloom stays warm until compact-filter coverage is genuinely sufficient.

Decision tree on sync start:
1. Connected peers with 0x40 ≥ `PEER_MAX_CONNECTIONS/2`: **compact mode**, no `filterload` sent.
2. Connected peers with 0x40 ≥ 1 but below threshold: **compact mode, single-source** — flag to user ("privacy-reduced compact filters, only 1 provider"). Still no bloom filter sent.
3. Connected peers with 0x40 = 0 and user setting is `Auto`: **bloom fallback** with non-scary banner.
4. Connected peers with 0x40 = 0 and user setting is `Compact filters only`: **hard error** with copy ("No compact-filter peers available. Add your own node in Settings, switch to Auto, or wait.") — do not silently send a bloom filter.
5. Never: send bloom filter under `Compact filters only` setting. This is the user's explicit sovereignty choice and the wallet must honor it even at the cost of not syncing.

## 8. Timeline estimate

Realistic, done-by-one-engineer-full-time:

| Block | Scope | Duration |
|-------|-------|----------|
| A | P2P handlers + service-bit plumbing in submodule (§1.1–1.2) | 1.5 weeks |
| B | Filter header chain + persistence + checkpoint verification (§1.3–1.4) | 1.5 weeks |
| C | Sync state machine + peer selection (§1.5–1.6) | 1 week |
| D | JNI bridge + Kotlin settings/UI (§2, §3) | 1 week |
| E | Seeder backend extensions + coordination with second operator (§4) | 1 week, parallelizable with D |
| F | Testing: unit, regtest integration, testnet soak (§6) | 2 weeks |
| G | Beta → staged release (§5.2 Gates C–D) | 3 weeks calendar |

**Focused engineering:** ~8 weeks. **Calendar:** ~12 weeks including beta soak. The ROADMAP's "4–6 weeks" figure assumes the GCS decoder is done (it is) and excludes calendar time for beta — realistically the honest number to quote a contractor is **10–12 weeks**.

Fast path if pressure exists: drop compact-filter-only mode and user-node settings from v4.0.0 (ship them in v4.1.0). That removes ~1 week and lets the release focus purely on the auto-path. Recommended only if coordination with a second seeder operator slips.

## 10. Explicit non-goals for v4.0.0

- Removing bloom filter code. Stays as fallback.
- Running a filter-proxy server. ROADMAP forbids it — filters come from peers, full stop.
- Neutrino-style "anchor point" trust (shipped checkpoints as authority). We only use shipped checkpoints as hints; runtime verification is mandatory.
- Changing the block header SPV path. Block headers continue to flow as before; only the tx-matching mechanism changes.
- Per-account filter scanning. The wallet scans one filter per block, checks against all watched scripts (all accounts). Finer-grained matching is a Phase 3 multisig concern.
