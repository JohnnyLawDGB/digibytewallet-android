## Why this exists (the pivot, in one paragraph)
The LAB acceptance of Track B wedged on a separate bug: `_BRPeerManagerClearMemory` pruned the scan-floor headers (retention tracked the cfheader frontier, not the cfilter scan frontier). Tasks 1–4 fixed that. The remaining requirement — a correct seed **always** restores, from genesis if needed — was first specced as a MAX_SPAN refusal gate (rejected: "a backup you can't restore from isn't a backup"), then as **sliding-window retention + a height→hash index**. A source-grounding fan-out proved BOTH wrong ([[feedback_ground_mechanism_against_source_before_spec]]): "free below the scan frontier" is a no-op (on a deep restore nothing lives below the frontier; the OOM is `[birth..tip]` pinned *above* the scan by the unpaced header fast-forward `BRPeer.c:622/638` filling `manager->blocks` before the scan starts); and the index is unimplementable-safe (the reorg/fork path `BRPeerManager.c:1655` never `BRSetRemove`s — no eviction hook for a height-keyed index — code already rejected it at `:2104`). The right mechanism: **pace the fetch so the header/cfheader frontiers stay a bounded window `W` above the cfilter scan frontier** — a convoy that climbs birth→tip together. Bounds `manager->blocks` to the window AND keeps `lastBlock` near the scan frontier, so the tip-down hash walk is short **by construction** — the deep walk stops existing rather than being optimized. Old wallets take longer; none are refused.

## Part A — the convoy gate (suppress the tip-racing continuations only)
Two windows, both keyed on the scan frontier = `BRCFScanLedgerLowestNeededHeight` (NOT raw `scannedThrough` — after a B2 abandonment `abandonedBelow` jumps without `_cfLedgerAdvance`, so LowestNeededHeight is current and `scannedThrough` lags):
- `W_hdr = blockHeaderFrontier − scanFrontier`, `blockHeaderFrontier = manager->lastBlock->height`.
- `W_cfh = cfHeadersFrontier − scanFrontier`, `cfHeadersFrontier = chain ? BRCompactFilterChainNextHeight(chain) − 1 : scanFrontier`. **NULL-chain carve-out (blocker B-3):** while `compactFilterChain == NULL` (fresh restore, before the first cfheaders response), the gate is treated as OPEN (`W_cfh := 0`) — never compute `NextHeight(NULL)−1` (it underflows to `0xFFFFFFFF`, which would falsely read the window as full and suppress the first request, deadlocking the fresh deep restore forever). **Extended in implementation:** an *empty* chain (`NextHeight == 0`, genesis-anchored, nothing appended) is the same case → also OPEN.

**Two further wedge-class guards (found during Task-2 implementation; each is a permanent sync wedge if removed — added to the design of record):**
- **ARMING GUARD — the gate is INERT until the CF scan is actually armed.** A `calloc`'d `BRPeerManager` has `cfLedger.scannedThrough == 0`, so `LowestNeededHeight == 1`; measured against a mainnet checkpoint tip that scores BOTH windows permanently full and would suppress the **block-header sync that must run FIRST** (and that `EnableAutoCompactFilterFetch` needs a tip from before it can even choose a floor) — a permanent wedge on every fresh start. `syncMode` also defaults to `BR_SYNC_MODE_BLOOM_ONLY` (==0) on a calloc'd manager, where there is no CF scan to pace at all. Guard: `syncMode != BLOOM_ONLY && autoFetchCFiltersEnabled` — every path that arms the scan sets that flag and `BRCFScanLedgerInit`s the ledger at a real floor together under the same lock, so it is a sound proxy for "the ledger holds a real scan frontier".
- **UNDERFLOW GUARD on both windows:** the scan frontier can legitimately sit ABOVE `lastBlock->height` (e.g. an abandonment watermark past a not-yet-synced tip); an unsigned wrap there reads as "permanently full" and wedges sync. Compare before subtracting.

## Part B — the KeepAlive convoy driver + structural-unservability valve (edge #1)
All of this lives in the KeepAlive tick (`:3354`, ~10 s, under the lock), after the existing residual drive. KeepAlive is the ONLY periodic driver; it must both un-suppress and unstick.

**B1 — the convoy driver (blocker-fix B-1).** Suppressing a continuation removes the only thing that re-fires it, and — critically — **the forward cfilter fetch's ONLY trigger is a cfheaders arrival (`:2656`)**, which the gate suppresses. So each tick, after recomputing both windows against the current LowestNeededHeight, drive whatever the convoy needs:
1. **Forward cfilter fetch (the missing driver):** if `outstandingCount < CF_OUTSTANDING_LOWWATER` **and** `autoFetchCFiltersThrough < cfHeadersFrontier`, issue the forward fetch DIRECTLY — do not wait for a cfheaders arrival. **It must mirror the CALLER-side steps the `:2656` path does (`:2657-2673`), not just the send:** compute `reqStop = min(cfHeadersFrontier, reqStart+MAX_CFILTERS_RESULTS-1)`, call `_BRPeerManagerRequestCFiltersLocked(reqStart..reqStop)`, and on a real send **set `autoFetchCFiltersThrough = reqStop` AND `BRCFScanLedgerRecordRequested(Dropped)` for the range** — `_BRPeerManagerRequestCFiltersLocked` internally does NEITHER (it only resolves the stop-hash + sends). Omitting them means `outstanding` never grows (back-pressure never engages) and, worse, the in-flight heights are untracked so `_cfLedgerAdvance` sails `scannedThrough` past an unscanned height = a silent gap. This is the load-bearing fix: without it, the resumed drain-trough (`outstanding==0`, `cfHeadersFrontier > scannedThrough+1`) has no way to create the first outstanding entry and the scan wedges silently.
2. **cfheaders advance:** if `W_cfh < W` and `cfHeadersFrontier < networkTip`, call `_BRPeerManagerRequestNextCFHeaders(peer, isConvoyAdvance=1)` on a filter-capable peer.
3. **getheaders advance:** if `W_hdr < W` and `blockHeaderFrontier < estimatedHeight`, re-issue the CF-only continuation from the block-header tip on the download peer.

**B1-resume — cursor reconciliation (important-fix, resume).** `enableAutoCompactFilterFetch(birth)` sets `autoFetchCFiltersThrough = birth−1` (`:4302`), and it is NOT persisted, so a resumed deep restore would re-request cfilters from BIRTH and `_cfLedgerAdvance` would drag `scannedThrough` back down — under convoy pacing (hours per descent) a frequently-backgrounded wallet would NEVER make durable progress. Fix: after `restoreCfScanLedger`, snap `autoFetchCFiltersThrough := max(autoFetchCFiltersThrough, restored scannedThrough)` (or persist the cursor). A resumed descent continues where it stopped.

**B2 — the abandonment valve, gated on proven CONNECTED-CF-SUBSET REFUSAL (operator GATE 1; fix I-1 + gate-verification GATE1 caveat).** The one permanent-stall mode is a gaveUp hole pinning LowestNeededHeight. But `gaveUp` (= `CF_REREQ_MAX_ATTEMPTS` exhausted) is only a HEURISTIC — during a convoy climb, retries can exhaust for transient/convoy-induced reasons (peer set rotated, fleet momentarily saturated). **A gaveUp on a canonical in-chain height during a healthy convoy is a pacing-bug signal, not a licence to abandon.** So the valve NEVER abandons on gaveUp alone; it proves refusal by the connected CF-peer subset first:
1. **Never abandon when it isn't the height's fault:** if NO connected CF-capable peer exists, do nothing (wait for a peer). Once RetireCapped moves a hole to gaveUp, NO driver re-requests it (both `NextRerequest`/`PeekRerequestRange` iterate `outstanding` only), so the valve must act, but only as below.
2. **Re-arm against the CURRENT (possibly-healed) peer set:** move the gaveUp hole back to `outstanding` with `attempts=0` (and **remove it from `gaveUp` on re-entry** — `_cfLedgerRemoveGaveUp`, so it has exactly one home and `gaveUpCount`/`gaveUp[0]` accounting stays correct) for a fresh full retry cycle; the residual driver rotates it across every connected CF peer (`30/60/120/120/120` = 7.5 min).
3. **Abandon ONLY on re-exhaustion PROVABLY offered-and-refused by live CF peers.** Two new per-hole fields on `BRCFOutstanding` (persisted with the ledger) make the proof possible — a `rearmCycles` counter and an `offersReachedLivePeer` per-cycle latch (set when a retry offer actually lands on a connected CF peer — Pass A breaks on `!chosen`, so `attempts` advancing already implies a live offer; the latch records that EVERY offer in the deciding cycle reached one). Abandon `AbandonGaveUpBelow(gaveUp[0]+1)` (WARN, `abandonedBelow` jumps, LowestNeededHeight advances, B1 reopens next tick) ONLY when: `rearmCycles ≥ CF_CONVOY_REARM_MAX (=2)` AND every one of the 5 offers in the final cycle reached a connected CF peer (offered+refused, not un-offered) AND ≥1 CF peer is connected at the abandon check. `REARM_MAX=2` (not 1) so a single unlucky peer-rotation/flap cycle cannot false-positive.

**Honest invariant + residual (gate-verification GATE1):** this proves refusal by the *currently-connected* CF-peer subset, NOT fleet-wide unservability — under documented fleet saturation (a canon oracle at `maxconnections`) a servable height's only serving node may never be consulted, so a transiently-unserved height CAN still be abandoned. That residual is deliberately bounded to a **GATE-3-recoverable inconvenience**: the abandoned band is surfaced (banner) and recoverable (node-reconcile covers any height CF-independently; a full rescan re-covers it — Part E). A slow-but-real height that any connected CF peer serves credits during the re-arm cycles and is never abandoned; the only remaining loss is a servable height NO connected peer had during ~22 min of rotated retry — surfaced and recoverable, never silent.

**Frontier source (B1/B2, blocker-fix I-6):** read a NEW native accessor `getLowestNeededHeight()` (= `BRCFScanLedgerLowestNeededHeight`). It is NOT `getCfScanLedgerCounts()[0]` — that index is `scannedThrough`, which lags LowestNeededHeight after a B2 abandonment.

**Self-healing modes inherited unchanged (do not re-solve):** (a) disconnect → `ReArmPeer` + residual re-dial; (b) pruned-scan-floor-header → cannot occur (Tasks 1–4). **(e) NEW — empty-outstanding + forward-cursor-behind-cfheaderFrontier → B1.1 forward drive** (the trough the panel found; neither residual nor valve can act on an empty array). (d) reorg → deep reorg re-inits the ledger at the floor (`:4035`); shallow reorg orphans a buffered hash that ages out. **Reorg is self-healing ONLY for heights above `scannedThrough` / for buffered hashes** — a reorged-in receive at a height already ≤ `scannedThrough` is a separate PRE-EXISTING gap (the fork path `:1653-1697` never resets `scannedThrough`), not solved here and not a convoy regression (deep-descent headers lag far below the tip; near-tip it is identical to today).

## Part C — window W + timing constants (arithmetic, not magic)
`CF_CONVOY_WINDOW W` = max the header/cfheader frontier may lead the scan frontier. **Floor (exceed all):** (1) scan lookahead `W ≥ CF_OUTSTANDING_MAX(4096) + MAX_CFILTERS_RESULTS(1000)` — smaller starves the scan; (2) cfheader quantum `W ≥ MAX_CFHEADERS_RESULTS(2000)`; (3) re-kick-latency margin at DGB ~15 s blocks. **Proposed `W = 10000`.** Three stated consequences: **max resident headers** ≈ `W+144 ≈ 10,144 × ~220 B ≈ 2.2 MB` (flat at any depth — the OOM is gone); **max prevBlock walk depth** = `W_hdr ≈ 10,000`, resolved by the Task-2 batch resolver ONCE per KeepAlive tick (sub-ANR, depth-independent); **scan-lookahead headroom** ≈ `4,900` blocks. *(Note M-5: the two windows share one `W`; at saturation `W_hdr = W_cfh`. `getcfheaders` `batchEnd` is clamped to `lastBlock->height` (`:2276`) so cfheaders can never overtake the block-header frontier and the stop-hash is always resolvable — no explicit "headers lead by 2000" invariant is needed or maintained; do NOT build a two-constant gate.)*

`CF_CONVOY_REARM_MAX = 2` — fresh retry cycles a gaveUp hole gets against a live CF-peer set before the valve abandons it (Part B2). The "generous time" that proves connected-subset refusal IS the re-arm cycles (2 × ~7.5 min ≈ 15 min of productive rotated-peer retry, ~22 min total including the original), not a bare timer; ≥2 so one unlucky peer-flap cycle cannot false-positive. **This is an ACCEPTANCE-INFORMED TUNABLE, not a blind constant (operator).** It is calibrated on how fast the *connected* CF-peer subset rotates through the fleet — and the accepted GATE-1 residual (fleet saturation) is precisely where rotation is SLOWEST (the peers you want are full; you cycle a degraded subset), so `=2` is most likely too small exactly where a wrong abandonment does its (recoverable) damage. Make it trivially adjustable (a single named constant, ideally runtime-readable) and INSTRUMENT abandonment: each `AbandonGaveUpBelow` logs the abandoned height range; the deep-restore acceptance correlates it against later `reconcile` success. **If a height abandons and then reconciles successfully, that is the signal `REARM_MAX` is tuned too tight — raise it — NOT that the valve is broken.** **Ordering invariant with the watchdogs (fix I-3):** while a gaveUp hole is pending re-arm/abandonment (`gaveUpCount>0` at LowestNeededHeight, or a re-arm cycle in flight), the re-keyed tip-stall watchdog's FAST/tier-1/tier-2 actions are SUPPRESSED (Part D) — the two scan-stall watchers must not race; the valve owns a known gaveUp stall and its re-arm IS productive work, so the watchdog defers rather than escalating churn.

**⚠️ BOUND THE SUPPRESSION (Task-5 review finding — the two mechanisms can conspire into a permanent stall).** The B2 latch is cleared by ANY disconnect of the peer stamped on the hole, and a deciding cycle is 5 offers over ~7.5 min — so on a churny fleet (canon oracles at `maxconnections`, errno-101 blips, ~8 peers rotating) every cycle can be tainted, the valve re-arms **indefinitely**, and the frontier stays pinned. Because the suppression above keys on "a gaveUp hole is pending re-arm", it is then **permanently active** and the watchdog stands down forever: the designed backstop never fires precisely in the case that needs it. **Therefore the suppression MUST be bounded** — suppress only while `rearmCycles < N` (or otherwise time-bound it), so an indefinitely-re-arming hole eventually re-exposes itself to the watchdog. Do NOT assume Part D rescues this case; it currently guarantees the opposite. The failure is a bounded-memory VISIBLE stall (the convoy gate holds `manager->blocks` flat at ~`W+144`), not an OOM or a silent wrong balance, and is user-recoverable — but it is the operator's "too reluctant = the wedge" direction and must not be left unbounded silently.

## Part E — progress display + abandonment surfacing (edge #3 + operator GATE 3)
`estimatedHeight` stays the network tip; the header-based `BRPeerManagerSyncProgress` (`:3663`) reads `lastBlock->height` = the convoy-capped `scanFrontier+W`, so it computes ≈ scan-progress + `W/chainLen` (near-accurate; **not** ~100% — fix M-3), over-reporting only the final ~`W` tail. - **Synced STAGE gate + banner key on an un-recovered-band signal, NOT `abandonedBelow` alone (blocker-fix B-2 + gate-verification GATE3(i)).** `abandonedBelow` is a monotonic hard floor that NEITHER recovery path clears, so gating Synced/banner on `abandonedBelow>0` directly makes recovery TERMINAL — after a successful node-reconcile the funds are restored but the wallet stays permanently non-Synced and permanently nagging. Instead track an **`abandonedBandRecovered` signal** (a pref, or a native "recovered-through" watermark): the Synced gate treats the abandoned band as scanned once recovery has covered it; the banner clears on the same signal. Until recovered, the abandoned band does NOT count as scanned (else "Synced" with a quietly short balance = the silent loss the valve exists to prevent).
- **Surface the abandonment (GATE 3):** add a native accessor for `abandonedBelow` + a cumulative abandoned-height count (fold into `getCfScanLedgerCounts` or a sibling). A **persistent main-screen banner** — "Part of your history (blocks X–Y) couldn't be verified from the filter fleet — tap to scan for missing transactions" — that SURVIVES the flip to Synced and clears only on the recovered signal. A WARN log is not a user surface.
