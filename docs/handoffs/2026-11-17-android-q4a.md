# Hand-off: Android adopted Digi-ID Q4 A

Written 2026-11-17 by the Android session, for the iOS-and-core session. It answers
`docs/handoffs/2026-11-13-android-digiid.md` in digibytewallet-ios, section by section.

## §1, which identity a site gets: adopted on Android in this change

- `IdentityKeyPolicy.choose(domain)` gives the shared key (`LEGACY`, m/0'/0/0) exactly when
  `domain` is `digiscope.me` or `api.digiscope.me`, compared character for character. Every other
  host gets its per-site SLIP-0013 key. Nothing else decides.
- Removed: the history grandfathering (`countSuccessfulLegacy`, and `countSuccessful`, are gone from
  `DigiIdHistoryDao`), `offersChoice`, the five-argument `choose`, `DigiIdManager.identityChoice`,
  `DigiIdViewModel.loadIdentityChoice` and `selectIdentity`, the identity card on the confirm screen,
  and its six strings in all 13 languages. The history's `derivation` column stays, as a record.
- **Which host is compared.** Android's `DigiIdRequest.domain` is OkHttp's host, which lower-cases
  the letters, and `isPlainAuthority` accepts no other respelling. iOS's `domain` is
  `host.lowercased()`. Both apps therefore read the list against the same lower-cased host, and
  `digiid://API.DigiScope.me/…` signs with the shared key on both (iOS's
  `testTheDomainComesFromTheParse`, carried as is). Deciding on the host as the request spells it,
  before lower-casing, would have split the two apps on exactly that request.
- **Cases.** `IdentityKeyPolicyTest.kt` carries every list case of `DigiIdIdentityTests`, value for
  value. It adds the empty host (per-site; a request with no host is refused, as on iOS) and the
  same hosts as parsed requests. `DigiIdIdentityChoiceTest.kt` drives `DigiIdManager`: a site with a
  shared-key login on record signs per-site, the history is written and never read, and each row
  records `legacy` or `site` (iOS's `testTheRecordedDerivationNamesAreAndroids`).
- Measured on Android's parser: a trailing dot (`digiscope.me.`) is accepted with the dot kept, so it
  gets the per-site key. iOS refuses it (§2). Neither app signs it with the shared key.
- User impact, from the release this ships in, for two groups of Android users:
  - A user whose history has a successful shared-key login to a site not on the list
    (io.digibyte ≤ 4.0.76 used the shared key everywhere) signs that site with its per-site key,
    and the site sees a new user.
  - A restored wallet, or one set up before 4.1.2, is no longer offered the shared key for a site
    it has no successful login to on this phone (4.1.2 to 4.1.4 offered it, through `offersChoice`),
    so a site that knows the user by the shared address sees a new user too.

  From that release on, both apps choose the same identity for every request both of them accept,
  which is the part of roadmap Stage 4's exit check ("the same key as Android for the same seed
  and site") that this decides.

## §2, the parser: still waits for Mark

`DigiIdRequest.parse` is unchanged.

## §3, the list in the core

The Android session builds `BRDigiIdUsesSharedIdentity` after Coinomi step 1 lands (Mark,
2026-11-17). Android then reads the list from the core through its bridge. The caller passes the
parsed, lower-cased domain, and the header compares byte for byte, as §3 says. Until then the list
is `IdentityKeyPolicy.DIGISCOPE_HOSTS`.

## Left as it is

- `NativeBridge.identityAddress` (`jni_wallet_sign.c`) has no Kotlin caller now, because the identity
  card was its only user. It stays, with its `digiid_core_kat` cases, until the core lane decides.
- The Coinomi design (`docs/superpowers/specs/2026-11-17-coinomi-digiid-design.md`, approved
  2026-11-17) predates this change. Four of its statements no longer hold:
  - "App: the policy" keeps the grandfathering;
  - the same section keeps `offersChoice`;
  - it says the approval screen shows the identity address "(it does today)", which only the card did;
  - its first anti-goal says no code change may move an existing wallet's identity, which Q4 A does
    on purpose.

  They need Mark before Coinomi steps 2 and 3.
